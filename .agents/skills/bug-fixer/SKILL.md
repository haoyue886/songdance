# 排障与修复

从复现、报错、相关代码和最近变更取证。先用已有信息调查，只有缺失的症状或预期无法推断时才问用户。允许提出假设，但明确它尚未证实。

- 用最小实验区分可能根因；记录已否定的假设，不机械重复失败操作。
- 一次验证一个因果假设；同一修复可以同步修改实现、调用者、迁移和测试，不人为限制成“一次只改一处”。
- 恢复既定行为无需重新访谈或改 Spec。预期本身改变时同步受影响的需求与计划。
- 服务异常先查日志、监听端口和进程归属。只处理本任务创建或明确授权管理的进程，不能把 CPU 低直接判作死锁。
- 按项目实际语言运行验证；对可重复的行为缺陷补有价值的回归用例。重现已消失且相关路径通过，才能说修复完成。
- 重复失败时重审假设、环境和范围，存在可执行调查就继续；明确缺少访问或关键信息时说明阻塞，不凭次数停止。

汇报根因证据、改动和验证结果。实质修复按 AGENTS 的风险规则进入独立审查，不机械重跑全项目审查，也不自动提交推送。
