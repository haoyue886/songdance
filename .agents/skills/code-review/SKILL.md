# 独立审查

由主 Agent 委派独立 code-reviewer 执行；没有委派能力时明确降级为主 Agent 自审。审查者只读代码，不修复、不提交、不改变验收标准。

## 范围

从用户指定范围、当前 diff 和受影响调用者开始。按需读取 Spec、计划和设计原文；缺少整套文档不阻塞局部审查。只有用户要求全项目审计或完整 Phase 验收时，才逐项覆盖整个对应清单。

同时检查需求符合度和实现质量，发现一个功能缺口不因此停止安全或数据问题检查。重点是行为错误、状态/并发问题、兼容性、权限、泄漏及测试盲区。文件长度、命名偏好或“Spec 没列出内部组件”本身不构成缺陷。

## 证据

- 追踪真实调用路径，说明触发条件、实际影响及代码位置；区分确认的问题与待验证假设。
- 检查关键测试是否使用可达输入和正确单位，是否覆盖失败路径；测试存在不等于验证充分。
- UI 变化在能运行时查看实际页面；不能运行则说明缺少视觉验证，不能凭 class 名宣称像素一致。
- 工具扫描结果需人工判断，示例变量名或合法路径不能直接当作密钥泄漏。依赖行为不确定时查锁定版本的官方来源。
- 可以运行与范围有关的隔离检查；已存在的有效证据可引用，不要求无关全量测试重跑。

## 输出

优先列可行动 findings，每项给优先级、文件行号、触发条件、影响和修复方向。P1 阻塞交付，P2 正常修复，P3 可选改进；紧急安全或数据损坏注明 P0。明确审查范围、验证方式、未覆盖项和结论。

没有确认的问题就写“在本次范围内未发现可行动问题”，不填充样式意见或宣称全项目无缺陷。复审定位修复及其影响面，新增跨模块风险才扩大范围。
