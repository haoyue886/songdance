# 设计规范

把产品目标和视觉偏好转成可执行的设计决定。已有设计稿、品牌资产、Brief 和页面先例优先于通用审美建议。

## 输入与路由

- 读取请求相关的 Product Spec、已有 Brief、设计稿和产品界面。没有 Spec 时，清楚的需求或现有产品也可作为输入；只有功能范围缺口会阻塞设计时才补需求。
- 新建方向时按需读 [新建工作流](references/workflow-0-1.md)；调整已有方向时读 [迭代工作流](references/workflow-iteration.md)。
- 只是把按钮、间距、文字或局部样式改成明确状态，且不改变设计约定：交实现处理，不重新采访或创建 Brief。
- 用户已有完整方向时直接整理，不强制寻找额外竞品和反参考，也不把专业细节变成用户答题。

## 设计决定

先识别实际承载形式：图形界面、终端、对话式 Agent、嵌入式扩展可以组合。图形界面关注页面、组件和设备布局；终端关注字符渲染与列宽；对话式 Agent 关注会话、运行态和任务控制。图形界面中的 Agent 仍使用图形界面视觉系统，不因“Agent”字样就套终端规范。

方向需要落到可观察属性，例如内容密度、对比、色彩、字体、空间与反馈。用户说“简洁”时，结合任务判断是减少步骤、减少元素还是加强层级，不套固定配方。工作台先保护画布、编辑区、预览或结果等主任务空间，再安排辅助面板。

只在缺失偏好会显著改变结果、且既有先例或用户授权无法解答时提问。可用少量方案和取舍帮助选择，也可提出合理默认后推进；不设固定轮数、参考数量或强制二选一。

## 交付与验证

1. 根据本次范围列出要解决的设计决定与完成标准。
2. 形成或局部更新 Brief，按 [模板](templates/design-brief-template.md) 裁剪。视觉 token 可以直接采用既有系统或合理默认，不必为每个值采访。
3. 核对核心流程、层级、适用状态、可访问性与目标载体，检查和功能需求是否冲突。
4. 用户已授权完整任务时继续设计稿、计划或实现；只请求 Brief 时交付文档及真正未决项，不设置阶段批准关口。

需要外部参考时核验具体来源，说明借鉴的属性。参考用来支撑当前设计，不以固定次数研究替代交付。
