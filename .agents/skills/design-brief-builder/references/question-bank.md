# 设计方向问题库

按当前缺失维度查阅。已有答案、项目先例或用户授权的合理默认都可作为输入，无需逐题询问；下面的检查项不是固定门槛。

## 1. 目标、受众与载体

**可问**：“用户打开它最重要的任务是什么？在哪个载体和设备上完成？”

**检查**：
- 图形界面以页面与组件为主，终端以字符输出为主，对话式 Agent 以会话和任务控制为主，嵌入式扩展遵守宿主约束。
- 这些形态可以叠加。网页聊天 Agent 仍有页面、字体、颜色和响应式；不把所有 Agent 都当成终端。
- 密度与节奏依据内容、任务和受众，而非用职业或年龄推断用户审美。

## 2. 感受、人格与原则

**可问**：
- “第一眼最需要表达什么感觉？它会影响哪些界面选择？”
- “你说‘高级/简洁/现代’，最在意的是色彩、信息量、留白，还是操作步骤？”

**检查**：抽象感受能转成可执行原则。例如“让核心结果先于辅助指标出现”能指导取舍，“好看”仍不足。原则数量由任务决定，不要求品牌人格故事。

## 3. 参考与边界

**可问**：“这个参考具体哪部分值得借鉴？有没有确定要避免的处理？”

**检查**：
- 分清参考的布局、密度、排版、颜色、动效与内容，避免把整个产品字面照搬。
- 跨形态参考可借视觉属性，不强行借不适用的信息架构。
- 用户没有反参考或已提供足够方向时直接推进，不为凑数量搜索。
- 示例文档和历史产品截图仅说明结构；当前产品事实需要另行核验。

## 4. 视觉系统

| 维度 | 需要决定时可问 | 可继承或默认的部分 |
|---|---|---|
| 品牌与主题 | 是否已有必须沿用的品牌资产、主题或色彩？ | 沿用现有系统，新增主题仅在范围需要时做 |
| 密度 | 用户主要阅读，还是频繁扫描和操作？ | 按任务安排间距与分组，保留可点区域 |
| 排版 | 标题、正文和技术内容谁是重点？ | 优先现有字体与字号层级 |
| 色彩 | 哪些动作与状态需要被强调？ | 克制语义色，不能只靠颜色表达状态 |
| 形状与层级 | 哪些区域需要分隔或突出？ | 继承组件圆角、边框、阴影 |
| 动效 | 哪个变化需要帮助理解？ | 功能性反馈，尊重减少动态效果偏好 |

具体 token 可由设计者据此定值，只有影响品牌或体验方向的关键取舍才向用户询问。中间值或混合方向可行时允许使用。

## 5. 图形界面结构与状态

**可问**：
- “最重要的结果和操作在哪里？导航、辅助信息与主区域如何分配？”
- “空数据、加载、错误或权限受限时，用户知道发生了什么以及下一步怎么做吗？”
- “实际支持哪些窗口或设备尺寸？收窄后优先保留什么？”

**检查**：
- 页面和主流程能对应需求，重点层级清楚；只覆盖存在的状态。
- 剪辑、设计、分析、编码等工作台优先保护画布、时间线、预览、编辑区或结果表。辅助信息先考虑既有侧栏、Tab、抽屉或上下文面板。
- 复用组件的状态与文案一致；键盘、焦点、标签、对比度及反馈适合目标载体。
- 不强制每个产品支持移动、平板和桌面全部设备。

## 6. 终端、对话与 Agent

| 维度 | 可问 | 检查要点 |
|---|---|---|
| 入口与模式 | 如何发起任务，是否需要命令、快捷键或模式？ | 与实际任务复杂度相称，不默认增加 slash 命令或多模式 |
| 呈现单元 | 消息、工具动作、代码、diff、长输出如何区分？ | 内容有层级，长输出可按需要折叠 |
| 运行态 | 等待、执行、流式返回、失败、中断分别如何反馈？ | 用户知道当前状态，有适合任务的控制入口 |
| 透明度 | 需要显示哪些计划摘要、进度、理由或动作记录？ | 以可用输出和高层解释设计，不要求公开模型私有推理 |
| 授权 | 哪些已授权动作直接执行，何种新操作需要决定？ | 展示产品已定义的授权边界，不擅自增加逐动作确认 |
| 恢复 | 中断后能否继续，错误后如何恢复？ | 保留必要状态并给可执行下一步 |
| 终端渲染 | 需要哪些字符、颜色与列宽兼容？ | 仅终端使用，图形界面不套 ANSI 规范 |
| 多载体 | 哪些载体本次要做？哪些体验应一致？ | 单载体不强加多载体预设计 |

## 7. 落地检查

文案清楚，空态提供适用的下一步；组件和设计变量优先复用。记录无法安全推断且会改变结果的未知，其他细节可以作为设计建议或默认值完成。完成标准是能交给设计或开发执行，不是收集尽可能多的偏好。
