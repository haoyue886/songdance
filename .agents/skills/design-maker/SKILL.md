# 设计稿制作

## 输入与范围

读取本次相关需求、Brief、已有设计稿与资产。设计稿决定实际视觉，Brief 约束方向，Spec 约束功能；用户最新明确要求优先。缺少某个文件不自动阻塞，已有输入足以出稿即可推进；只有会显著改变结果的功能或视觉缺口才补问。

使用用户指定或项目已有的设计工具和文件。没有指定时选择当前可用、适合交付物的工具；只有工具选择会影响交付用途时才询问。工具不可用时明确限制，并在授权范围内交付可行替代，例如局部原型或设计规格；不得把替代物宣称为已完成的原生设计稿。

## 制作

1. 按请求提取页面、组件与适用状态清单，给出简短执行步骤和验收标准。完整产品覆盖约定范围，局部修改只处理相关部分；已授权制作时直接开始，不等待清单的二次批准。
2. 读取所用工具的必要指南，复用已有变量和组件。新建项目根据 Brief 建立够用的变量和重复组件，不为单次元素过度组件化。
3. 制作页面或更新局部，用有代表性的真实内容验证层级与布局；未知事实用明确的示例内容，避免把示例当产品事实。
4. 覆盖与交互有关的空、加载、错误、权限、成功等状态，无关状态不机械补齐。
5. 用工具预览或截图检查布局、溢出、对比、焦点、组件一致性及目标尺寸，修正发现的问题，并核对需求覆盖。

## 完成与衔接

交付可定位的设计成果、范围和验证结果，明确实际未完成项。只有完成且验证的交付物才标为完成。用户已授权后续开发时继续计划或实现；只请求设计稿时交付设计稿，不以固定阶段交接要求再次批准。
