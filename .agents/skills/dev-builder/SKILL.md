# 开发

先定位目标代码、相关需求与现有测试。新项目按已选技术路线搭建；已有项目沿用实际结构。没有完整 Spec 或 DEV-PLAN 不阻塞明确的小任务，跨模块或需求不明时才补规划。

## 实现约束

- 以可验收的行为组织工作，任务粒度由依赖和风险决定，不强制每个组件单独审查、提交。
- 修改公共接口、常量、组件或数据结构前查调用者；持久化格式变化要处理存量数据，并验证迁移或兼容路径。
- UI 复用现有样式和组件，验证实际渲染、响应式布局及相关错误/加载/空状态。新需求确需新组件时允许设计；不伪造真实数据或未实现的按钮行为。
- 遵循项目类型约束和结构，不用固定文件行数代替设计判断。只为实际复杂度拆分，不为假想需求抽象。
- 使用现有依赖和锁定版本；新增能力先查项目先例和框架原生能力，不确定 API 查官方文档。
- 集成测试使用隔离的配置、数据与进程，释放本任务创建的资源。

## 验收

先运行能验证变化的最小有效检查，再按共享面和风险扩大回归。使用项目实际语言和命令，不给 Python 修复套 TypeScript 检查。

实质变更按根 AGENTS 的批次要求派独立审查，向审查者提供改动范围、需求位置和验证证据。修复发现后重验受影响路径；新的跨模块影响才扩大审查。Phase 完成时对照交付清单和明确验收门槛，不能以局部测试替代整阶段验收。

交付说明行为变化、已跑命令及结果、未验证或受阻事项。Git 操作遵循本次授权；不由 hook 自动推送，也不要求用户重复确认已授权的开发阶段。
