# 开发计划

把本次范围拆成有依赖顺序、可独立验收的交付单元。计划服务于执行，不承担重复需求采访或审批流程。

## 输入与路由

- 读取相关需求、现有 DEV-PLAN、实际代码和必要设计依据。优先用 Product-Spec.md；没有文件但任务已明确时，可据已知范围规划，不强制补齐整套文档。
- 已有明确且可执行的 Phase，用户要求继续开发：直接交 dev-builder。只有发现真实阻塞或范围变化时局部修计划。
- 小型、耦合紧的变更用简短步骤即可，不为套模板新增 Phase。
- 新项目或复杂变更使用 [计划模板](templates/dev-plan-template.md)，按需保留技术栈、数据变化和风险部分。

## 规划原则

- 每个 Phase 交付一个可验证的能力或必要的风险验证结果。基础设施应服务于最早可运行路径，不自动占满一个大阶段。
- 按真实依赖排序，尽早验证高不确定、失败后会改变方案的部分；不要用固定交付物数量决定粒度。
- 根据仓库事实列关键文件或模块及其用途。新项目路径可以标“拟建”，实施时校准；不为了路径精确而编造现有文件。
- 验收描述用户可观察结果和适用检查，区分计划中的检查与已通过的证据。不要把通用四步仪式复制为每个改动的硬门槛。
- 技术栈优先遵循项目已锁定版本与约束。新的选型或不确定兼容性核验相关官方资料，不默认升级到最新版本。合理技术选择可给建议并推进，只有会显著改变结果的未决取舍才问。
- 拟投入生产的模型、数据或外部能力涉及许可与运行环境限制时，先确认这些约束能支持目标用途，再安排昂贵验证；不把专项审计扩展到无关任务。

## 生成与更新

1. 定义本次目标、范围和完成标准，检查需求到交付项的覆盖。
2. 梳理依赖、阶段、关键文件、风险与验收；不确定项标明解决方式和是否阻塞，不能把未验证假设写成事实。
3. 创建计划或仅修改受影响的阶段。保留已完成事实和证据；变更触及已完成工作时追加返工项或新阶段，不假装原结果仍满足新要求。
4. 核对依赖与范围，用户已授权实施时继续执行。用户只要求计划时止于计划交付，无须以“要不要下一步”作为固定结束语。

DEV-PLAN 的 Phase 编号只指技术交付阶段，保持已有编号以便进度与证据可追踪。模板不定义 commit、push、发布或权限策略。
