# 新产品需求工作流

适用于没有可用需求文档的新产品。先吸收用户已提供的要求和相关材料，再判断缺口；资料已充分时直接写作。

## 从目标到可开发需求

1. **界定目标与范围**：识别主要用户、要完成的任务、当前问题、首版结果与明确排除项。验证产品价值时，真实行为比假想意愿更有用；用户只要求实现已定方案时，不强制补市场验证访谈。
2. **展开主路径**：把用户从入口到完成任务的过程写清，提取功能、数据对象和关键分支。对每个关键功能补触发、行为和结果。
3. **补风险与验收**：考虑实际存在的空数据、加载、错误、权限、恢复等状态，以及影响本产品的非功能约束。AI 或 Agent 仅在相关时展开专项。
4. **形成文档并核对**：按 [需求模板](../templates/product-spec-template.md) 裁剪，检查当前范围覆盖、条目之间一致、假设可辨认。

以上是分析维度，不是必须逐个等待用户点头的阶段。可调整顺序、合并处理、跳过无关内容；[问题库](question-bank.md) 只读取当前缺口对应部分。

## 何时提问

缺失信息会显著改变要做的产品，而且用户没有授权合理默认或现有材料不能解答时才问。比如面向个人还是团队会改变权限与数据模型，值得澄清；按钮圆角通常可以沿用设计系统。

问题尽量具体，附选择后果或建议。确认已明确的要求不需要再获得一次批准。可在简短摘要中暴露假设并继续非依赖工作；真正阻塞的决策得到答案前，不执行依赖它的步骤。

## 完成标准

- 读者能据此实现本次范围内的主流程和关键异常，不必猜核心业务行为。
- 每项关键要求有可观察的验收结果；事实、合理假设和待验证目标分开记录。
- 未解决问题标明是否阻塞，非阻塞细节不会被写成无止境的采访清单。
- 如需跨文档引用，沿用或建立稳定的 REQ / FLOW 等编号；小项目可采用更简短结构。

交付后继续用户已授权的后续环节；仅在用户只要 Spec，或下一步需要新的关键决定时结束于文档交付。
