# 生产环境运维手册

使用结构化日志和经过哈希处理的任务标识符。切勿在工单中粘贴原始文件名、音频、完整对象键、签名 URL、Redis 内容或凭据。

## 首次响应

1. 检查 API `/health`、Railway 部署状态，以及最近的 API、Worker 和 Cleanup 日志。
2. 检查 PostgreSQL、Redis 和对象存储服务商的状态。
3. 若故障可能导致数据丢失或成本无限增长，降低 `SONGDANCE_DAILY_JOB_LIMIT` 以停止新任务。该值必须为正数；使用 `1`，不要使用 `0`。
4. 重启服务前，保留日志和受影响的哈希任务 ID。

## API 不可用

- 迁移失败：检查 Alembic 错误和数据库连通性。生产环境中不要启用 `SONGDANCE_AUTO_CREATE_SCHEMA`。
- HTTP 403 `UNTRUSTED_PROXY`：确认请求只经 Railway 公网入口进入，再将 `SONGDANCE_TRUSTED_PROXY_CIDRS` 设置为精确的边缘对等 CIDR，并使 `SONGDANCE_TRUSTED_PROXY_HOPS` 保持为实际代理层数。绝不能用 `/0` 来“修复”。
- 浏览器 CORS 失败：将 `SONGDANCE_CORS_ORIGINS` 设置为精确的 HTTPS Vercel 源站，然后重新部署 API。不要使用 `*`。
- HTTP 413：保持 25 MB 的产品限制；应排查客户端，而不是提高限制。

## 队列积压或任务卡住

- 确认 Worker 正以一个副本运行，并监听 `SONGDANCE_QUEUE_NAME`。
- 检查 Redis 连通性和 RQ 的失败注册表。任务最多重试两次。
- 若模型内存耗尽反复发生，停止接收新任务，重启 Worker，保留一个副本，并在恢复容量前提高容器内存。
- 活跃配额预留仍存在时，不要手动重复入队相同任务 ID。

## 模型或产物失败

- `NO_NOTES_DETECTED`：这是有效的终态结果；请用户提供更清晰的独奏钢琴片段。
- 模型超时或报错：从镜像中确认 FFmpeg 与模型运行时版本，然后仅在现有的三次尝试上限内重试。
- MusicXML 或时间线失败：MIDI 可能仍可下载；检查具体产物状态，不要将整个任务标记为成功。
- 任何模型或后处理变更，都需要重新执行固定的 10 段音频人工质量门禁。自动化合成音符评分不能替代该门禁。

## 存储或删除失败

- 确认存储桶凭据仅允许对生产存储桶执行列举分段上传、终止分段上传、读写和删除操作。
- 在 Cleanup 服务中执行一次 `python -m app.jobs.cleanup`，并确保 `cleanup_cycle.failed=0` 后再恢复其 Cron。
- `DELETE_FAILED` 任务必须保持失败状态可见，以便清理程序重试。对象仍存在时，不要删除数据库行。
- 将服务商的一天生命周期规则作为备份，不要用它替代应用程序清理。

## 配额与成本保护

初始上限为：每个 IP 每小时 3 个任务、每个客户端 1 个活跃任务、全局 2 个活跃任务、每天 25 个任务。第一周每天检查 Railway CPU/内存、Redis 使用量、数据库大小和存储桶字节数。每次只提高一个限制；更高的 Worker 副本数会成倍增加模型内存和计算成本。

若成本意外升高，将每日限制设为 `1`，保持 YouTube 禁用，让当前任务完成，并在修改基础设施前检查事件计数。

## YouTube 事故

除非已审查运营区域，否则保持 `SONGDANCE_YOUTUBE_ENABLED=false`。平台拒绝、私有/登录/区域/付费/直播限制和超时，都必须回退到本地上传。绝不添加 Cookie、浏览器配置文件、代理绕过或登录令牌。

## 恢复验证

任何事故或回滚后，必须验证：`/health` 返回 200、一次匿名上传、刷新后恢复、乐谱和钢琴卷帘渲染、三种有效下载、立即删除、一次成功的 Cleanup 周期，以及桌面端和 375 px 宽度下浏览器控制台无报错。
